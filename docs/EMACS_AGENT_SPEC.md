# Emacs Agent — техническое задание и план реализации

**Статус:** согласованная спецификация для первого релиза (MVP)  
**Дата:** 13 октября 2026 г.  
**Язык реализации:** Emacs Lisp  
**Основная зависимость:** [gptel](https://github.com/karthink/gptel)  
**Рабочее название пакета:** `emacs-agent` (можно переименовать без изменения архитектуры)

> **Инструкция кодинговому агенту:** Реализуй этот проект как самостоятельный Emacs Lisp-пакет. Начни с исследования фактического API установленной/выбранной версии `gptel` и короткого end-to-end spike. Затем выполняй план по этапам. При расхождении спецификации с реальным API выбирай устойчивые публичные интерфейсы, документируй отклонения и сохраняй функциональные требования. Не подменяй универсальный `eval_elisp` набором ограниченных инструментов и не внедряй подтверждения каждого действия по умолчанию.

## 1. Цель и основная идея

Создать ИИ-агента, естественно встроенного в работающий Emacs. Агент взаимодействует с LLM посредством `gptel` и получает **полный доступ к текущему процессу Emacs** через один инструмент — выполнение произвольного Emacs Lisp (`eval_elisp`).

Emacs является единой, живой, общей средой: агент видит существующие буферы, окна, функции, переменные, minor/major modes, пакеты, процессы и файлы; может читать и изменять их прямо во время работы. Нет копии редактора, отдельного песочничного процесса или искусственно ограниченного набора редакторских API.

При этом **контексты LLM-сессий независимы**: одна глобальная сессия для буферов вне проектов и одна сессия на каждый определённый проект. Разделение относится к истории общения с моделью, а не к привилегиям или видимости объектов Emacs.

### Ключевые принципы

1. **Emacs-first:** вся оркестрация и пользовательский интерфейс пишутся на Elisp; внешний runtime не нужен.
2. **Один универсальный инструмент:** `eval_elisp` предоставляет доступ к Emacs API, shell и сторонним пакетам; модель исследует среду самостоятельно.
3. **Полные полномочия:** произвольное исполнение Elisp без sandbox и обязательных approval-подтверждений. Это осознанное требование пользователя.
4. **Единая среда:** сессии разделяют один Emacs; действия агента влияют на реальные буферы и файлы.
5. **Project-scoped conversation:** истории проекта и глобальной сессии не смешиваются.
6. **Минимальное вмешательство в рабочий процесс:** запрос вводится из текущего рабочего буфера в многострочном минибуфере; журнал агента read-only.
7. **Разделение данных и представления:** структурированная история диалога отделена от форматированного журнала событий.
8. **Переиспользование gptel:** не реализовывать HTTP, провайдеров и протоколы LLM заново, пока это не подтверждено объективной несовместимостью.

## 2. Словарь

- **Рабочий буфер:** буфер, из которого пользователь вызвал команду агента; не минибуфер и не журнал агента.
- **Сессия:** история диалога с LLM, привязка к проекту (или глобальному пространству), активная/ожидающая задача, журнал, настройки.
- **Запрос пользователя / turn:** один ввод пользователя вместе со снимком метаданных Emacs на момент отправки и всеми последующими шагами tool calling до финального ответа.
- **Задача / run:** выполняемый агентный цикл одного turn; включает несколько вызовов LLM и инструмента.
- **Журнал событий:** человекочитаемый read-only буфер, отображающий user, assistant, reasoning (если доступен), tool calls, tool results, errors и статусы.
- **История модели:** сериализуемые структурированные сообщения, которые реально используются для построения следующих API-запросов.
- **Контекст редактора:** снимок буфера, файла, проекта, `point`, строки/колонки, выделения, `default-directory` и mode при отправке запроса.

## 3. Поведение сессий

### 3.1. Разрешение сессии

При отправке нового запроса:

1. До открытия минибуфера захватить исходный рабочий буфер и окно, если оно живо.
2. В контексте исходного буфера попытаться определить проект через стандартный `project.el`: `project-current` и `project-root`.
3. Если проект найден, нормализовать его корень (`expand-file-name`, `file-name-as-directory`, при необходимости `file-truename` с осмысленной обработкой ошибок/удалённых путей) и выбрать сессию по этому ключу.
4. Если проект не найден, выбрать единую глобальную сессию.
5. Если подходящей сессии ещё нет, создать её лениво при первом запросе или при явном показе журнала.

**Не использовать basename директории как уникальный идентификатор.** Два одинаково названных проекта с разными путями — разные сессии. Для TRAMP и удалённых путей не разрушать идентичность путём локальной каноникализации.

Автоматически созданная сессия существует на протяжении жизни Emacs и (после реализации persistence) между перезапусками.

### 3.2. Поведение при смене буфера

- Сессия назначается **при отправке каждого нового пользовательского запроса**, а не при каждом переключении буфера.
- Уже выполняющаяся задача остаётся привязанной к исходной сессии, даже если агент или пользователь переключил буфер, открыл файл другого проекта или изменил активное окно.
- Новый запрос из другого проекта выбирает соответствующую сессию.
- Новый запрос из буфера журнала не должен ошибочно определять проект по самому журналу: использовать привязку журнала к сессии либо явно определённый последний рабочий буфер. Это поведение документировать.
- Агент свободно читает/изменяет объекты за пределами своего проекта; проектная сессия — **контекст разговора, не граница доступа**.

### 3.3. Одновременные задачи

- В рамках одной сессии не исполнять несколько конфликтующих агентных циклов одновременно.
- Запрос, отправленный в занятую сессию, помещать в FIFO-очередь; показывать это в журнале. После завершения предыдущего run следующий использует контекст, захваченный при **его собственной отправке** (не переснимать его молча).
- Разные сессии могут одновременно ожидать LLM-ответы.
- Все исполняемые Elisp-выражения работают в одном процессе Emacs; одновременная активность не означает безопасной изоляции между сессиями. В MVP выполнять вызовы инструментов последовательно в общем event loop; явную глобальную очередь tool execution можно добавить, если асинхронные callbacks приводят к конфликтам.

## 4. UX: команды и журнал

### 4.1. Минимальные публичные команды

Рекомендуемые имена (можно уточнить согласно именованию пакета):

- `emacs-agent-ask` — открыть многострочный минибуфер, принять запрос, отправить в сессию исходного буфера.
- `emacs-agent-show` — показать read-only журнал соответствующей сессии.
- `emacs-agent-cancel` — остановить активный run текущей/указанной сессии; не уничтожать историю.
- `emacs-agent-session-list` — показать/выбрать созданные сессии (допускается через `completing-read` для MVP).
- `emacs-agent-save` — явно сохранить состояние; автоматическое сохранение по завершении run.

Для MVP не требуется отдельная полноэкранная оболочка или сложная панель управления. Не перехватывать глобальные клавиши без явной пользовательской настройки.

### 4.2. Ввод в минибуфере

- Поддерживать многострочный ввод.
- `RET` отправляет, `C-j` вставляет перевод строки; `C-g` отменяет ввод. Учесть реальные keymaps Emacs и `read-from-minibuffer`.
- `M-p`/`M-n` перебирают историю пользовательских запросов; не включать в неё автоматически сгенерированные метаданные.
- Для длинных запросов предусмотреть штатный Emacs-путь редактирования минибуфера в отдельном буфере (например, `C-M-c`/`edit-minibuffer` в зависимости от режима и версии); не создавать собственный редактор без необходимости.
- Отправка пустого или состоящего из пробелов текста не создаёт API-запрос.
- Исходные `buffer`, `window`, `point`, `mark`, region, project и `default-directory` должны быть зафиксированы **до входа в минибуфер**. При длительном вводе контекст остаётся снимком момента вызова команды (выбрать и явно задокументировать именно эту семантику).

### 4.3. Read-only журнал сессии

Отдельный буфер на сессию, например `*emacs-agent: global*` или `*emacs-agent: <project-name>#<short-id>*`. Имя человекочитаемо, идентичность — по ключу сессии; избегать коллизий.

Журнал показывает в хронологическом порядке:

- пользовательские сообщения;
- ассистентские сообщения (потоково, если поддержано);
- reasoning/thinking — **только когда модель/провайдер реально предоставляет его**, без выдуманных реконструкций;
- вызов инструмента: имя, переданные аргументы/Elisp-выражение, статус;
- результат инструмента: текст/ошибка (длинные выводы можно сворачивать);
- сетевые/API-ошибки и отмены;
- состояние текущего run: waiting, streaming, tool-running, completed, error, cancelled.

Read-only означает, что пользователь не редактирует журнал напрямую; сам пакет вставляет текст с временным `inhibit-read-only`. Пользователь может выделять/копировать текст и использовать стандартные средства перемещения. Для инструментов/результатов применить текстовые свойства и/или overlays, чтобы их можно было сворачивать в дальнейшем.

**Отдельные источники правды:** (а) сериализуемые события/сообщения, (б) построенное из них визуальное представление. Не восстанавливать API-историю путём чтения форматированного текста журнала.

Streaming не должен безусловно перемещать `point` пользователя, если тот читает старые записи. При нахождении в конце допустимо follow-tail.

## 5. Контекст редактора в каждом пользовательском запросе

Для каждого нового turn формировать снимок:

- session type (`global`/`project`) и canonical project root, если есть;
- имя рабочего буфера и `buffer-file-name`, если есть;
- `major-mode`;
- `default-directory` рабочего буфера;
- позиция `point` (число в координатах Emacs);
- `line-number-at-pos` и `current-column` (оговорить 1-based строку и 0-based колонку);
- `region-active-p`, при наличии — `region-beginning`, `region-end` и **опционально сам текст выделения** с конфигурируемым порогом длины;
- можно хранить marker для локальной навигации, но **не сериализовать Lisp marker как часть истории API**; абсолютная позиция в метаданных — снимок, который может устареть после редактирования.

Минимальный текстовый формат для LLM:

```text
<emacs-context>
session: project
project-root: /home/user/work/app/
buffer: src/main.py
file: /home/user/work/app/src/main.py
major-mode: python-ts-mode
default-directory: /home/user/work/app/src/
point: 1248
line: 52
column: 16
region-active: true
region-start: 1190
region-end: 1294
</emacs-context>
```

Данные должны однозначно кодироваться/экранироваться, чтобы имя буфера или пользовательский текст не имитировали границы секции. Контекст — диагностическая информация, **не инструкция более высокого приоритета**. Не передавать автоматически полный текст буфера: агент читает нужные диапазоны через инструмент.

Различать `nil` file для не-файловых буферов и пустую строку; поддерживать narrowing: в system prompt пояснить, что доступная область буфера может быть сужена, а инструмент вправе вызывать `widen` при необходимости.

## 6. Политика хранения метаданных

Нужно три режима, настраиваемые через `defcustom`:

```elisp
(defcustom emacs-agent-context-history 'current
  "How automatically captured Emacs context is sent to the model."
  :type '(choice
          (const :tag "Disabled" nil)
          (const :tag "Current user turn only" current)
          (const :tag "All user turns" full))
  :group 'emacs-agent)
```

- `nil`: не прикладывать автоматические метаданные к API-запросам; обычный текст пользователя остаётся.
- `current` (**по умолчанию**): прикладывать снимок только к **текущему активному пользовательскому turn**; сохранять этот снимок во всех последующих запросах к LLM, необходимых для tool calling в рамках данного run; при переходе к новому turn исключать метаданные прошлого turn из входящей истории API.
- `full`: сохранять и передавать метаданные каждого user turn.

**Важнейший инвариант:** отображаемая пользовательская реплика всегда содержит только написанный им текст; системная метаинформация не должна незаметно становиться частью редактируемой истории пользователя.

Хранить логическую структуру `{user-text, editor-context, tool-calls, tool-results, ...}` независимо от конкретной сериализации API. Текущую историю API строить из неё согласно режиму. Для `current` не удалять исходные метаданные безвозвратно из внутреннего журнала: они могут понадобиться для отладки, переключения режима и воспроизводимости (их долговременное сохранение отдельно регулируется политикой persistence).

**Ограничение:** `gptel` может хранить provider-specific opaque tool/reasoning данные; нельзя произвольно удалять необходимую protocol-связность, включая tool-call IDs и результаты. Не нарушать связи между assistant tool call и tool response при фильтрации контекста. Сделать интеграционные тесты этого режима.

Мотив: снизить количество устаревших метаданных, которые запутывают модель. Влияние на prompt caching зависит от провайдера, порядка сообщений и реализации кэша; не обещать улучшение или ухудшение без измерений. Стабильный system prompt и структурированная история помогут кэшированию.

## 7. Универсальный инструмент `eval_elisp`

### 7.1. Требования

Экспортировать модели один основной tool: `eval_elisp(expression: string) -> string`.

Он исполняет произвольный Emacs Lisp **в текущем процессе Emacs без sandbox, искусственного белого списка функций и обязательных подтверждений**. Доступны:

- все доступные Elisp-функции, переменные, хуки, пакеты, окна, буферы;
- чтение/редактирование буферов;
- открытие/сохранение/удаление файлов;
- `project.el`, `xref`, LSP, Dired, Org, Magit и другие установленные расширения;
- системные команды и процессы через Emacs (`process-file`, `shell-command-to-string`, `make-process` и т. д.);
- определение функций и команд, которые остаются доступны в текущем процессе после tool call.

**Полный доступ намеренный.** Не вводить approval UX, sandbox или политику запрета shell без отдельного запроса пользователя. При этом явно документировать последствия и необходимость доверенного model endpoint: произвольное выполнение может менять конфигурацию, читать секреты, запускать дочерние процессы и удалять файлы.

### 7.2. Семантика вычисления

- Принимать строку с **несколькими последовательными Lisp-формами** (не ограничиваться первым `(read ...)`). Вычислять их по порядку; возвращать печатное представление результата последней формы, дополнительно учитывая stdout от `princ`/`message`, если возможно и полезно.
- Корректно различать успешный `nil` и ошибку.
- Ошибки чтения, `eval` и исполнения преобразовывать в информативный результат с типом, сообщением и, по возможности, backtrace (без незаметного прерывания сессии).
- Обрезать **только отображаемую/передаваемую моделью форму вывода** при превышении конфигурируемого лимита и явно указывать, что ответ усечён; не обрезать вычисление и не искажать возвращаемое значение до печати.
- Обрабатывать `quit` и отмену так, чтобы `C-g`/cancel не оставляли задачу в вечном состоянии running.
- Определить динамический контекст tool execution: исходный рабочий буфер run (если ещё жив), otherwise разумный fallback (`session` buffer или буфер запуска) с явным сообщением в prompt. **Не считать автоматически, что `current-buffer` равен буферу, выбранному пользователем в момент выполнения инструмента.** Агент может явно использовать `with-current-buffer`.
- Нельзя случайно выполнить пользовательскую строку дважды при повторной доставке callback; каждый tool call должен иметь идентификатор в состоянии run.

### 7.3. Shell и долгие операции

MVP **не имеет отдельного shell tool**. Достаточно:

```elisp
(shell-command-to-string "git status --short")
(process-file "rg" nil t nil "-n" "defun" ".")
```

Для долгих задач использовать асинхронные процессы Emacs (`make-process`, sentinels, buffers). Если необходим механизм ожидания/опроса результата процесса, сначала проверить пригодность существующих Emacs API; при потребности разрешён небольшой Elisp helper (но не новый публичный LLM tool на MVP).

Синхронные команды и тяжёлый Elisp могут блокировать UI. Не обещать неблокирующее исполнение произвольного Lisp; документировать ограничение.

После MVP провести сравнительный эксперимент: реальные задания с одним `eval_elisp` против `eval_elisp` + `shell`; измерить надёжность, число tool calls, время и качество. Добавлять `shell` только на основании результатов.

## 8. gptel: границы ответственности и технический spike

`gptel` отвечает за LLM API, провайдеров, модели, авторизацию, HTTP/streaming и provider-specific форматы. Пакет `emacs-agent` отвечает за выбор сессии, сбор контекста, очередь задач, UX, формирование истории и журналирование событий.

**Подтверждённые точки входа:** `gptel-request` позиционируется авторами как API для сторонних команд и интерфейсов; `gptel-make-tool`, `gptel-tools`, `gptel-use-tools` обеспечивают инструменты; в `gptel` есть hooks для tool lifecycle и reasoning. **Но:** `gptel-request` сам по себе не предоставляет UI и стандартные callback/обвязку `gptel-send`; надо проверить, кто контролирует следующий запрос после результата tool call, streaming и сохранение истории.

### Обязательное исследование перед основной разработкой

1. Зафиксировать поддерживаемую версию/коммит `gptel`, минимальную поддерживаемую версию Emacs и детали использования `gptel-request`.
2. Прототип: одна текстовая реплика → gptel → один `eval_elisp` tool call → результат → продолжение модели → финальный ответ.
3. Проверить серию из **нескольких** tool calls; поддержку API-tool IDs и ordering; повторные попытки, ошибки, отмену.
4. Проверить streaming текста, инструментов и доступного reasoning; какие события реально доступны через публичные callbacks, а какие — лишь через внутренние функции.
5. Проверить механизм передачи ручной структурированной истории и фильтрации metadata старых turn без повреждения цепочки tool messages.
6. Проверить буферно-локальные и динамические настройки `gptel`: выбранный backend/model, tools, prompt и context. Не менять глобальную пользовательскую конфигурацию `gptel` ради агента.
7. Сверить реальные сигнатуры `gptel-request`, `gptel-make-tool`, callback и hooks в **выбранной версии**. Не переносить без проверки фрагменты кода из старых примеров; API менялся.
8. Подготовить краткий `docs/GPTEL_INTEGRATION.md`: подтверждённые возможности, ограничения, используемые публичные интерфейсы и fallback-решения.

**Правило:** использовать публичный API. Если необходима внутренняя функция `gptel--...`, изолировать зависимость одним адаптером, указать минимальную совместимую версию и тест на совместимость. Не копировать сетевую реализацию `gptel`.

При необходимости реализовать **собственный небольшой agent loop**, который использует `gptel-request` только для отправки/приёма сообщений. Это допустимо и предпочтительнее хрупкого использования стандартного редактируемого chat UI.

## 9. Предлагаемая архитектура кода

```text
emacs-agent/
├── emacs-agent.el             # public commands, customization, initialization
├── emacs-agent-session.el     # session registry, project resolution, queue
├── emacs-agent-context.el     # capturing and rendering editor context
├── emacs-agent-gptel.el       # gptel adapter and agent run state machine
├── emacs-agent-eval.el        # eval_elisp implementation + output formatting
├── emacs-agent-log.el         # structured events + read-only transcript view
├── emacs-agent-storage.el     # persistence and restore
├── test/
│   ├── emacs-agent-session-test.el
│   ├── emacs-agent-context-test.el
│   ├── emacs-agent-eval-test.el
│   ├── emacs-agent-log-test.el
│   ├── emacs-agent-storage-test.el
│   └── emacs-agent-gptel-test.el
├── docs/
│   └── GPTEL_INTEGRATION.md
└── README.md
```

Названия файлов допускается упростить, если это улучшает архитектуру. Избегать преждевременного раздробления на десятки модулей.

Пример состояния (не обязательная точная схема):

```elisp
(cl-defstruct emacs-agent-session
  id key project-root events messages log-buffer
  pending-runs active-run updated-at)

(cl-defstruct emacs-agent-run
  id session user-text editor-context source-buffer
  source-window status request-handle tool-call-ids)
```

События должны иметь стабильный идентификатор, тип, время, session/run ID, полезную нагрузку; не сериализовать напрямую живые Emacs buffer/window/process объекты. История API может строиться из событий или храниться в отдельной нормализованной структуре, но без дублирования источника правды и расхождения между ними.

### Состояния run

```text
queued -> preparing -> requesting -> (streaming) -> tool-running
                                    ^                 |
                                    |_________________|
                     -> completed | failed | cancelled
```

Должны быть определены переходы при сетевой ошибке, ошибке инструмента, закрытии буфера и отмене. Никакие поздно пришедшие callbacks от отменённого run не должны модифицировать историю или продолжать цикл.

### System prompt (смысл, не буквальный текст)

Инструктировать модель, что она работает внутри общего Emacs, имеет единственный инструмент `eval_elisp`, может исследовать функции через `documentation`, `describe-function`, `symbol-function`, переменные через `boundp`/`symbol-value`, буферы через `buffer-list`, а проекты через `project.el`. Данные `<emacs-context>` описывают положение пользователя при постановке задачи, но могут устареть. По необходимости пользоваться shell через функции Emacs. Не предполагать, что весь файл автоматически включён в prompt; читать необходимое самостоятельно. Не придумывать результаты выполнения инструментов.

## 10. Persistence и восстановление

- Сессии хранить в пользовательском каталоге Emacs (`user-emacs-directory` или настраиваемом `emacs-agent-data-directory`), **не в рабочем Git-репозитории по умолчанию**.
- Сохранение событий/истории и метаданных сессии: версия схемы, session key/root, настройки/параметры модели, timestamps, сообщения, результаты инструментов, доступный reasoning.
- Не записывать в файл живые объекты Emacs (buffers, markers, processes, closures, request handles). Ссылки на буферы восстанавливаются заново или помечаются недоступными.
- После перезапуска история читается и показывается в прежней сессии; активные задачи **не возобновляются автоматически**, отображаются как interrupted.
- Выполнять атомарную запись через временный файл и переименование; обрабатывать частично повреждённые данные и не терять все сессии из-за одного файла.
- Автосохранение после завершения/отмены run и в осмысленных промежуточных точках, чтобы минимизировать потерю длинных агентных циклов.
- Документировать, что история/результаты инструментов могут содержать секреты. Не выводить API-ключи в логи программы; данные сессий имеют обычные файловые права пользователя, отдельного шифрования MVP не требует.
- Восстановление должно сохранять tool-call связь, необходимую для повторного обращения к провайдеру. Если формат backend несовместим после обновления, показывать понятную ошибку/путь миграции.

## 11. Отмена, ошибки и надёжность

- `emacs-agent-cancel` помечает run отменённым, прекращает активный HTTP-запрос средствами `gptel` (если поддерживается) и игнорирует поздние callbacks.
- Отмена **не откатывает уже выполненные изменения файлов/буферов** и не гарантирует остановку внешних процессов, запущенных произвольным Elisp. Не обещать обратное.
- Ошибка конкретного tool call возвращается модели как tool result, если протокол допускает продолжение; критическая transport/protocol error завершает run с явным статусом.
- Обеспечить верхний предел на размер отправляемого текстового результата, максимально допустимое число последовательных tool calls для защиты от случайных бесконечных циклов (допускается настраиваемый soft limit без снижения полномочий инструмента); при достижении лимита показывать состояние и позволять пользователю продолжить. Это не sandbox.
- Вести нормальные диагностические сообщения для разработчика, но не смешивать их с визуальной историей без необходимости.
- При невалидной/уничтоженной сессии и stale callback не выполнять действия.

## 12. Настройки

Минимальный набор `defcustom`:

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `emacs-agent-context-history` | `current` | `nil` / `current` / `full` |
| `emacs-agent-data-directory` | внутри `user-emacs-directory` | Хранилище сессий |
| `emacs-agent-eval-output-limit` | разумный лимит, напр. 32 KiB | Максимальный текст tool result для модели |
| `emacs-agent-region-text-limit` | напр. 8 KiB | Максимальное автоприложение выделения |
| `emacs-agent-max-tool-calls` | напр. 100 (настраиваемо) | Защита от ошибочной бесконечной итерации |
| `emacs-agent-stream` | `t` | Потоковое отображение при поддержке backend |
| `emacs-agent-show-reasoning` | `t` | Отображать только доступные reasoning-данные |

Использовать выбранный пользователем backend/model из `gptel` или предоставить их настройку **на уровне агента** без неявного изменения глобальной конфигурации. При создании сессии зафиксировать понятную политику переключения модели (использовать текущую или хранить модель в сессии); для MVP можно использовать текущий `gptel` backend/model на каждый новый run, сохраняя использованные значения в событиях.

## 13. Тесты и качество

Использовать ERT, запускать по возможности в `emacs -Q --batch`. Для сетевых тестов имитировать `gptel-request` и его callback — чтобы CI не требовал API-ключей. Отдельно предусмотреть **необязательный** ручной end-to-end тест с реальным провайдером.

Обязательные сценарии:

1. Буфер вне проекта → общая сессия; два разных непроектных буфера разделяют её.
2. Два проекта с одинаковым basename, но разными root → две разные сессии.
3. Два файла одного проекта → общая проектная сессия.
4. Смена буфера во время запроса → текущий run остаётся в исходной сессии.
5. Минибуфер не подменяет информацию о рабочем буфере/point/region.
6. Снимок метаданных правильно обрабатывает nil file, неактивное выделение, narrowing, удалённый `default-directory`.
7. Режим `nil`: метаданные отсутствуют в API; `current`: только активный turn и всё его tool continuation; `full`: все turn.
8. `eval_elisp` выполняет несколько форм, печатает результат, возвращает информативную ошибку, различает `nil`/error, усечение явно обозначено.
9. Несколько tool calls подряд: результат каждого корректно включается в следующий запрос.
10. Tool failure не разрывает структурированную историю без явной ошибки.
11. Отмена с последующим поздним callback не меняет историю и не стартует новый tool call.
12. Два run в одной сессии исполняются последовательно; очередь захватывает context каждого запроса отдельно.
13. Две разные сессии могут независимо ждать ответ LLM.
14. Журнал защищён от ручного редактирования, но обновляется во время streaming без перемещения курсора читателя.
15. Save/restart/restore восстанавливает историю и project mapping; interrupted run не возобновляется автоматически.
16. Провайдер без reasoning не получает выдуманных reasoning-блоков.
17. Пакет не ломает существующие `gptel-tools`, `gptel-backend` и пользовательские хуки в других буферах.

Ручные end-to-end задачи:

- Попросить агента перечислить буферы, определить `major-mode` и прочитать участок текущего буфера.
- Попросить найти функцию в проекте, используя `project.el` или `rg` через Emacs.
- Попросить изменить пару файлов и проверить видимые изменения буферов.
- Попросить запустить тесты CLI и интерпретировать результат.
- Переключаться между глобальной и проектными сессиями; перезапустить Emacs и продолжить диалог.
- Отправить второй запрос во время активной работы и проверить очередь.

## 14. Этапы реализации и критерии готовности

### Этап 0 — Исследование gptel (обязательно перед основной реализацией)

**Результат:** `docs/GPTEL_INTEGRATION.md` и работающий минимальный spike, осуществляющий одну полную цепочку пользователь → LLM → `eval_elisp` → LLM → ответ. Обозначить API-риски, принять решение о собственном минимальном state machine поверх `gptel-request`.

**Готово, когда:** есть воспроизводимый ручной сценарий и тест/фиксированный mock; версия `gptel` зафиксирована; понятно, как получать tool/reasoning/stream события.

### Этап 1 — Сессии и захват контекста

Реализовать проектные ключи, глобальную сессию, структуры run/session, сбор контекста до минибуфера, `emacs-agent-ask` с многострочным вводом, минимальный system prompt.

**Готово, когда:** из буферов разных проектов создаются верные сессии; captured metadata не относится к минибуферу; ERT-тесты зелёные.

### Этап 2 — Agent loop и eval

Подключить `gptel-request`, обработку tool call / tool result, последовательные вызовы, завершение, исключения, отмену, очереди по сессии. Полный `eval_elisp`, включая multiple forms.

**Готово, когда:** агент способен прочитать и изменить буфер, воспользоваться shell через Elisp и дать итоговый ответ; нет повторного исполнения tool call из-за callbacks.

### Этап 3 — Журнал и streaming

Создать read-only major mode/буфер истории, event renderer, индикацию статуса, потоковую вставку, отображение доступного reasoning, отображение инструментов и ошибок; добавление UX-команд.

**Готово, когда:** весь цикл виден в отдельном журнале, а рабочий буфер остаётся доступным; обычное чтение старых записей не прерывается автопрокруткой.

### Этап 4 — Метаданные и история

Реализовать режимы `nil/current/full`, структурированное хранение событий, корректную историю API и проверку связности tool calls; ограничения длины метаданных и выводов.

**Готово, когда:** автоматические метаданные отсутствуют в отображаемых пользовательских репликах; `current` не удерживает старые снимки в новых API-запросах, но сохраняет текущий снимок во время собственного tool loop; ERT тесты всех режимов зелёные.

### Этап 5 — Persistence, полировка и документация

Долговременное хранение, восстановление, обработка прерываний, README (установка, настройка gptel, keybindings, команды, риски полного eval), batch tests, пользовательские сценарии.

**Готово, когда:** новый Emacs восстанавливает сессии и позволяет продолжить разговор, пакет не изменяет глобальное состояние `gptel` неожиданным образом, manual smoke tests пройдены.

### Этап 6 — Исследование shell (не блокирует MVP)

Сравнить модели и типы задач на одном `eval_elisp` и связке `eval_elisp + shell`. Записать факты: количество запросов, время, ошибочные вызовы, надежность и сложность кода. **Не реализовывать второй инструмент автоматически без результатов.**

## 15. Out of scope для MVP

- MCP и интеграция внешних MCP-серверов;
- специализированные LLM tools (`read_file`, `edit_file`, `grep` и т. д.);
- отдельный shell tool (только исследование после MVP);
- собственный HTTP/LLM backend вместо `gptel`;
- sandbox/ограничение полномочий и approval на каждый вызов;
- отдельные процессы Emacs для агентов;
- сложная UI-панель, отдельный frontend или web UI;
- многопользовательская работа, распределённые сессии и синхронизация;
- самостоятельный индекс проекта/векторный поиск;
- автоматический rollback всех изменений при отмене;
- обязательный доступ к скрытому reasoning (выводить только доступные API-данные).

## 16. Нефункциональные требования

- Совместимость с типичным пользовательским Emacs и существующей настройкой `gptel`.
- Отсутствие сетевого блокирования UI во время ожидания LLM при поддержке backend.
- Предсказуемая обработка системных ошибок, отмены, закрытых буферов и перезапуска.
- Минимальная зависимость от недокументированных интерфейсов `gptel`.
- Достаточное ERT-покрытие core logic и возможность тестировать без LLM API-ключей.
- Документированные ограничения: синхронный Lisp может блокировать Emacs; процессы и последствия выполненных действий нельзя полностью отменить; model endpoint имеет высокие полномочия.
- Привычные Emacs conventions: `defgroup`, `defcustom`, docstrings, lexical binding, стандартные keymaps, byte compilation без предупреждений в собственной части пакета.

## 17. Правила выполнения задачи кодинговым агентом

1. Сначала изучи установленную версию Emacs и актуальную версию `gptel`, не предполагая точные сигнатуры API.
2. Покажи в коде небольшой end-to-end spike; определи надежную интеграционную границу.
3. Реализуй пакет итеративно, обеспечивая запускаемый промежуточный результат на каждом этапе.
4. Пиши тесты на функции выбора сессий, захвата контекста, политики истории, сериализации и управления callbacks.
5. Не изменяй пользовательские global `gptel-tools`, `gptel-use-tools`, prompt или backend как побочный эффект подключения пакета.
6. Не усложняй схему доступа: **полный eval является не ошибкой проектирования, а намеренным свойством**.
7. Там, где требуется выбор из нескольких способов интеграции, предпочтение: публичный API gptel → минимальный адаптер → изолированное использование внутренних функций только при необходимости.
8. Запускай ERT-тесты и byte-compile; фиксируй, что проверено автоматически, а что требует реального LLM.
9. Документируй принятые решения и ограничения; не выдавай не реализованные функции за готовые.
10. Выполни работу в последовательности этапов выше; не трать время на второстепенные расширения до завершения MVP.

## 18. Критерий завершения MVP (определение Done)

Пользователь работает в исходном Emacs-буфере, вызывает `emacs-agent-ask`, вводит многострочную задачу и отправляет её. Агент автоматически выбирает глобальную или проектную сессию, передаёт LLM текущие метаданные, самостоятельно исследует Emacs через `eval_elisp`, читает/меняет буферы и при необходимости запускает CLI посредством Emacs. Все сообщения, доступный reasoning, инструменты и результаты появляются в отдельном read-only журнале. Следующие запросы в том же проекте используют прежнюю историю, а другие проекты изолируют собственные истории; все они воздействуют на единый Emacs. Метаданные предыдущих запросов не попадают в контекст модели при режиме `current`. Сессии переживают перезапуск Emacs. Отмена, ошибки и несколько последовательных вызовов инструмента обрабатываются корректно.
