# ADR-0017: Проверяемый рецепт edit → save → check

Статус: согласовано пользователем, реализовано и проверено offline.

## Причина

В следующем пользовательском OCaml-диалоге новая диагностика правильно указала
ошибочные API. Основная оставшаяся проблема — после правки модель несколько раз
проверяла старый файл на диске, хотя результат хелпера уже содержал `:modified t`.
Также наличие команд/режима было выдано за работающую проверку языка, а exit status
внешних команд терялся. Приватные диалоги не копируются в репозиторий и не
переисполняются; сокращение числа вызовов не считается контролируемым benchmark.

## Решение KISS

Нет нового model tool, process runner, checker registry, автоматического выбора
backend, сохранения, запуска проверки или восстановления редактора. Прежний
unrestricted `eval_elisp` и хелперы сохраняют семантику; изменения — в инструкциях,
исполняемом примере и предметном сообщении ошибки.

Системный prompt теперь явно требует:

1. Изменить → явно сохранить, когда это нужно → проверить → перечитать изменённые
   области после последней проверки. Отдельно сообщать edited/saved/checked.
2. Дисковые команды не проверяют несохранённые изменения. Не сохранять/отбрасывать
   пользовательские изменения автоматически ради запуска проверки.
3. Требовать integer exit 0, а не пустой stdout, прежде чем объявлять успех или
   запускать собранный binary.
4. Не путать наличие команды/feature, активность backend и реально проверенный код.
   Читать minor-mode variables, а не вызывать mode commands ради их состояния.
   Обращаться к документированным diagnostics/readiness/freshness фактически
   настроенного checker; при его отсутствии использовать проектную check command.
5. Исполняется Emacs Lisp, не Common Lisp; для незнакомых функций доступны
   `fboundp`, `documentation`, `help-function-arglist`.

Восьмой пример использует `process-file` в отдельном `with-temp-buffer`, объединяя
stdout/stderr через `(t t)`. Он возвращает `:exit`, `:output`, `:directory`,
`:checked-file`, не выбрасывает статус и не переиспользует старый output buffer.
Без visited file или при modified buffer пример останавливается до запуска,
не вызывая `save-buffer`. Это безопасный шаблон для адаптации, не новое runtime
ограничение eval. Для намеренной проверки несохранённого текста нужен checker,
работающий с буфером, либо явно согласованная другая стратегия.

CHECKER, argv и cwd пользователь/модель адаптируют к реальному проекту. В argv
передаётся `file-local-name`, identity результата остаётся исходным visited path.
`process-file` синхронный: длительные проверки требуют подходящего существующего
асинхронного workflow, а не обещания неблокирующего выполнения этого примера.

Прежние семь примеров, read/continuation, coordinate, tick, atomic undo и save
contracts сохранены. Текст уплотнён: 5033 символа вместо 4984, всё ещё ниже прежней
границы 5037. Это сравнение символов, не измерение token savings или качества LLM.

`emacs-agent-read-lines` по-прежнему не обрезает END молча. Выход за EOF теперь
сообщает запрошенные START–END и фактический whole-buffer `:total-lines`, включая
правила empty buffer/terminal newline. Point/restriction/tick не меняются.

## Проверка и пределы

341 ERT, clean warnings-as-errors compilation и diff-check. Все восемь реальных
fenced примеров prompt исполняются через evaluator. Дополнительные regressions:

- несохранённый/непосещающий файл буфер не запускает process и не сохраняется;
- edit → отказ disk check → explicit save → check → reread;
- пустой output с exit 2 и signal string не превращаются в успех;
- каждый вызов имеет новый пустой output buffer и убирает его после завершения;
- mocked argv/destination/cwd/file identity и неизменность исходного текста/undo;
- реальный отдельный синтетический CHECKER печатает stdout/stderr и завершает exit 2;
- EOF сообщает реальные bounds и сохраняет narrowing/point/tick.

Нет provider calls, hot-load пользовательского Emacs, запуска пользовательского
OCaml-кода или установки пакетов. Новое поведение самой модели ещё не измерено:
тесты доказывают работоспособность примеров/контрактов, не послушание unrestricted
модели. Реальная интеграция с конкретным Merlin/LSP backend — не часть этого шага.
